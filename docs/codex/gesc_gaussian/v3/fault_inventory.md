# V3 fault and recovery inventory

Planning audit, 2026-09-25. Companion to the [V3 plan](plan.md) and [status](status.md). This document records existing behavior and proposes classifications; it changes no runtime policy, thresholds, source code or retained result.

**V3 must keep the base translating during Gaussian verification and design.** A rotating sensor arm, rotation in place, or stationary acquisition does not satisfy this requirement. Evidence can be reacquired while translating only when a sufficiently fresh valid control direction and command authority remain available. When they do not, a protective stop is appropriate and the continuous-motion outcome is marked interrupted. No planned stationary fallback is selected.

## What this audit establishes

`FAILSAFE` is a software label, not a consequence ranking. Existing code uses it for an explicit operator stop, unavailable input, internal contract inconsistency, escape timeout and other conditions of very different importance. Several other faults with significant consequences never enter that state: startup refusal, local arm FAULT, lost recording, invalid offline evidence, or a sensor stream repeatedly resetting.

The supervisor is an algorithm owner, not merely a logging node. It chooses states and objective weights, manages Gaussian transactions and owns escape/recenter contributions. It can be simplified, but deleting it without assigning those responsibilities elsewhere changes the algorithm and its command authority. The current node also retains substantial optional historical behavior that is not selected by the last V2 scenario.

The strongest indirect failure chain in current simulation is:

```text
late/missing/conflicting support or source data
  -> synchronization/filter history invalidated or output unavailable
  -> controller sees no fresh valid filter input for its deadline
  -> controller publishes zero and EVENT_FAILSAFE
  -> supervisor permanently latches controller_fault
```

The filter may be capable of recovering on the next valid measurement while the integrated run is already terminal. Conversely, moving candidate cancellation, unsuitable fill preparation and several verification deadlines already return to SEARCH. Neither “everything recovers” nor “every bad sample causes FAILSAFE” accurately describes the code.

## Rank consequence separately from current response and likelihood

These are engineering priorities, not failure probabilities. The retained attempts do not supply a representative probability estimate, and an emitted FAILSAFE does not prove a catastrophe was imminent. “Could technically keep running” and “may safely continue under the stated control contract” are different claims.

| Priority/class | Consequence if ignored | Examples | Proposed V3 policy; recovery scope |
| --- | --- | --- | --- |
| **1 — H0: actuation or physical safety integrity** | Potentially severe physical harm or uncontrolled motion; worst credible class, without claiming it occurred | Failed neutral command, conflicting actuator writers, invalid/unbounded command, collision/obstruction not otherwise protected | Inhibit motion immediately through the appropriate command/actuator owner; explicit inspection/rearm for persistent integrity faults. Some hazards below are not detected by this code. |
| **2 — H1: safe control unavailable** | Robot could continue moving blindly or on obsolete direction/pose; substantial task and possible physical consequence | Essential pose/direction/owner lost, sustained callback starvation, expired motion authority | Protective zero with bounded recovery policy after coherent fresh inputs. Continuity is interrupted; never refresh obsolete data or blindly hold velocity. |
| **3 — C: configuration/state integrity** | Wrong algorithm, coordinate/time basis or contradictory objective could invalidate all subsequent decisions; severity can rise to H0/H1 | Wrong frame/run/schema, clock discontinuity, registry-chain conflict, mixed installed code or wrong Bash selector | Refuse startup, or revoke affected authority and start a coherent epoch/new run. No automatic reinterpretation of corrupted identity. Exact report formatting failures alone do not belong here. |
| **4 — M3: mission or strategy failure** | Failure to escape, progress or identify the intended source; generally not an emergency by itself | Escape timeout, exhausted retries, no usable candidate over bounded attempts | Abort/cancel the failed strategy; continue translating with a valid safe SEARCH direction where supported, otherwise protective stop. Retain the failed mission result. |
| **5 — A2: temporary estimator/evidence degradation** | Reduced accuracy or a lost candidate; often technically and safely recoverable | Sparse revolution, weak mean, isolated delayed/bad sample, rejected fit, candidate departure | Discard affected evidence and continue bounded translation only while independent fresh valid control remains. Measure degradation/recovery; escalate when control actually becomes unavailable. |
| **6 — E4: recording/evaluation quality** | Incomplete or untrustworthy experiment report; algorithm might still operate | Vicon evaluation dropout, missing diagnostic/report, bag writer failure without essential-owner loss | Mark evidence incomplete; retain operational control independently unless an explicit experiment policy requires stopping. Such a stop is an evidence-policy decision, not proof of physical hazard. |
| **N — normal completion/interruption** | Intended cessation, not a fault severity | Ctrl+C, operator stop, goal hold, finite run deadline | Stop cleanly; label the initiating reason separately from expected downstream authorization revocation. |

Current-response codes used conceptually below: **T** terminal supervisor latch; **Z** zero/inhibit without a latch event; **A** admission withheld until readiness/timeout; **R** sample/window/candidate reset or recovery; **X** recorder/process run abort; **L** local actuator/sampling fault latch; **O** offline evidence failure only. One initiating event can propagate through several codes. Attribute the first cause rather than counting the cascade as several independent defects.

## Four different ways a protection can disappoint

| Failure of protection | Meaning | How V3 should measure it |
| --- | --- | --- |
| False-positive trip | The guard rejects data or stops a run even though a safe useful command remained available | Capture the exact predicate and original timestamps; compare with independent truth and retained support. Do not call every conservative rejection a false positive without this evidence. |
| Missed fault | A dangerous or invalid condition occurs without the checked predicates detecting it | Inject the named fault and inspect actual motion/actuator state independently of the software label. Uncovered physical hazards are listed below. |
| Slow detection | The correct condition is eventually detected, after a harmful or unacceptable delay | Measure acquisition-to-detection and detection-to-command latency in wall time under load; a ROS timer deadline alone is insufficient. |
| Failed stopping | Software requests zero/neutral but the actuator or base does not stop, or stop evidence cannot establish it | Separate requested stop, applied command, observed motion and proof deadline. Failed actuation is H0; missing timely proof is uncertainty that must not be relabeled standstill. |

A source-delivery gap does not prove the Arduino stopped acquiring; serial framing, support admission, publication and callback service can fail separately. A GPIO callback timestamp does not prove the exact encoder edge time. A nominal servo RPM does not prove actual shaft or arm speed. Preserve these distinctions when attributing a trigger.

## Simplification and testing implications

Keep a small explicit motion-authority owner and one final `/cmd_vel` writer. Separate sample validity, direction confidence, fill suitability, strategy progress, experiment completeness and actuator safety rather than propagating all of them through one generic fault label. A logger can observe these states without being in every essential callback path; a deliberate recorder-required commissioning mode can remain explicit.

Reuse existing owners and validated mathematical components. Compute expensive estimates when new data arrives, cache immutable configuration, and publish bulky diagnostics at an explicit rate. Use one authoritative sample identity and observed support record so multiple subscribers do not reconstruct supposedly identical geometry from different histories. Avoid repeated JSON/hash/deepcopy work in high-frequency callbacks where an immutable record or revision reference suffices. Retain finite queues, deadlines and source identities.

A local missing sample should invalidate only evidence that actually depends on it when this can be demonstrated. The current head-of-line join and whole-history reset policy can turn one bad datum into a long absence of direction. A recovery change must prove that the remaining control direction is fresh and valid while the base translates; it cannot silently reuse stale velocity or declare stationary reacquisition successful.

Test the first-cause families independently before combining them: source loss/jitter, support delay, serial buffering, identity conflicts, phase reversal/stall, stale output, recorder load/loss, process starvation/death, clock discontinuity, and command/stop supervision. Compare commanded speed, measured translation, estimator availability, sample age, CPU headroom, mission behavior and recording quality separately. A successful protective stop in an outage test passes the safety-response criterion while failing or interrupting continuous-motion behavior.

This inventory does not support a new unchanged 15 Hz trial, blanket timeout inflation, a stationary verification fallback, or another unbounded autonomous physical repair cycle.
